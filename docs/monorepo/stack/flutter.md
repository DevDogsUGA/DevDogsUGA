# Flutter

`apps/study-group-finder` is the repo's only Flutter app: Dart SDK `^3.5.0`, `supabase_flutter ^2.8.0`, owning the `study_group_finder` Postgres schema. It is still a placeholder — `lib/main.dart` renders `StudyGroupFinderApp` and tables are added as the app is built. Read this if you are working on that app, or if you are about to reorder `[api] schemas` in `supabase/config.toml` and wonder who cares. The Flutter SDK is needed for nothing else in the repo; [Flutter's docs](https://docs.flutter.dev) teach the framework.

## The package.json is a Turborepo wrapper

The app has a `package.json` that runs no JavaScript. It exists so turbo can see `dev`, `build`, `test`, `lint`, `typecheck` and `generate-types` for this app like any other. Three of them — `build`, `dev` and `generate-types` — shell out to Flutter through `with-env -c`:

```bash
pnpm dev --filter study-group-finder   # local stack auto-detected, else remote
```

`-c` is load-bearing. The scripts need `$API_URL`, `$PUBLISHABLE_KEY` and `$SECRET_KEY` to expand from the loaded `.env` rather than from the ambient environment, and `-c` defers expansion until after `with-env` has loaded the files. Values reach Dart as `--dart-define`s: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `AUTH_MODE` from `NEXT_PUBLIC_AUTH_MODE`.

The other three call their tools directly, with no `with-env` in front: `lint` is `flutter analyze`, `test` is `flutter test`, and `typecheck` is `tsc --noEmit` over the wrapper's own TypeScript rather than over Dart.

> [!WARNING]
> `"type": "module"` in that manifest is load-bearing too. Without it, tsx compiles `env.ts` as CommonJS, whose `require()` of the ESM `@devdogsuga/env` creates a **second registry instance** — `declare()` then registers into a copy nobody reads, and the app's variables silently vanish from the generated `.env.example`. Vitest ESM-ifies everything, so the completeness test cannot catch it.

## Dart models come from supadart

`supabase gen types` has no Dart target, so models are generated by the community [supadart](https://pub.dev/packages/supadart) package (`supadart.yaml`), run through `pnpm --filter study-group-finder generate-types`.

supadart cannot select a schema: it reads whatever PostgREST serves as its default profile. That is the entire reason `study_group_finder` is listed **first** in `[api] schemas` — see [Supabase](/docs/monorepo/stack/supabase). It is safe because every other client sets `db.schema` explicitly.

<details>
<summary>Why is <code>analyzer</code> pinned to 13.x, and what uses it?</summary>

`analyzer ^13.0.0` is a dev dependency used only by `tool/docs_extract.dart`, which reads this app's declarations so `docs-build gen` can emit a Dart reference — the Node-side generator has no way to analyze Dart. It is held at 13.x because the Flutter SDK pins `meta 1.18.0`, which analyzer 14.x will not resolve against. That extractor is also why the docs highlighter registers the `dart` grammar: without it, every generated signature would fall back to plain text and lose its highlighting silently.

</details>
